# AuditWorkbench 设计思路

## 一、产品定位

### 为什么叫 AuditWorkbench？

**Workbench** = 工作台，不是平台(Platform)、不是系统(System)、不是工具集(Toolkit)。

"工作台"意味着：
- 审计人员在这里完成完整的工作，而非使用零散功能
- 从原材料(审计资料)到成品(疑点报告/取证单/底稿)的完整流水线
- AI 在后台默默辅助，人是台前的主角

### 与"审计知识工坊"的关系

| | 审计知识工坊 | AuditWorkbench |
|------|-------------|----------------|
| 定位 | 知识库系统 | 实务操作平台 |
| 核心 | 法规检索、匹配、遴选 | 智能分析、文书生成、定性辅助 |
| 用户行为 | 查、找、匹配 | 分析、判断、生成 |
| AI角色 | 检索增强 | 多智能体伴随 |

两者互补：知识工坊提供"弹药"(法规知识)，AuditWorkbench 完成"战斗"(审计分析)。

## 二、用户理解

### 国家审计人员的工作特点

1. **责任重大**: 每一个结论都可能成为证据，必须可追溯、可复核
2. **专业性强**: 精通审计业务但不一定是技术专家
3. **流程严格**: 有固定的审计程序和文书规范
4. **时间紧迫**: 审计项目有明确的时间节点
5. **层级分明**: 审计员→主审→复核→审理，层层把关

### 核心诉求

- **信任感**: 不是"AI替我做决定"，而是"AI帮我整理，我来做判断"
- **安全感**: 每步都可回退，每个结论都可溯源，每次操作都留痕
- **效率感**: 一键确认全部AI推荐，不逐条点击
- **掌控感**: 可以自定义模板、表达式、法规依据，系统适配我的工作方式

## 三、交互设计哲学

### "提交→确认→执行"三段式

这不是技术限制，而是设计选择。为什么要让用户确认？

```
AI推荐 ──→ 人工确认 ──→ 自动执行
  ↑            ↑           ↑
  快           稳          准
```

- AI 负责"快": 秒级从2195个模型中匹配、从40万部法规中检索
- 人负责"稳": 用自己的专业判断确认或修正AI建议
- 系统负责"准": 确认后全自动执行，不打扰用户

### 一键确认 ≠ 放弃控制

一键确认是**效率工具**，不是**偷懒工具**：
- 全部AI推荐预勾选，一键采纳 → 适合常规场景
- 低置信度项自动标⚠️提示 → 降低风险
- 逐条可展开修改 → 保留精细控制能力

### LLM智能伴随

LLM不说话，而是**在用户需要时给出专业提示**：

| 不是 | 而是 |
|------|------|
| "AI判断该字段正确" | "该字段置信度0.67，建议核对原始文档第3页" |
| "AI建议选这部法规" | "审计对象为市级单位，建议优先适用省级规定" |
| "AI发现12条违规" | "表达式将扫描4810条记录，预计命中约12.9%" |

## 四、三大工坊的命名逻辑

```
┌─────────────────────────────────────────┐
│           AuditWorkbench                 │
│                                          │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
│  │知识工坊   │ │数据工坊   │ │资料工坊   │   │
│  │Knowledge │ │Data      │ │Document  │   │
│  │Workshop  │ │Workshop  │ │Workshop  │   │
│  └────┬────┘ └────┬────┘ └────┬────┘   │
│       │           │           │         │
│  静态知识沉淀  动态数据加工  原始资料管理  │
│  (已知的)      (正在产生的)  (待处理的)   │
└─────────────────────────────────────────┘
```

- **知识工坊**: 沉淀的"已知" — 2195个违规模型 + 40万部法规 + 典型案例
- **数据工坊**: 正在产生的"新知" — 非结构化资料→结构化→可查询→可分析
- **资料工坊**: 待处理的"原料" — 上传的文档 + 提取模板 + 重新推理

三者形成闭环：资料工坊输入原料 → 数据工坊加工为结构化数据 → 知识工坊反哺知识库

## 五、差异化设计决策

### 1. 为什么不做深色科技风？

面向政府审计人员，不是面向开发者或科技爱好者。

- 政府蓝(#1a3a5c) + 中国红(#c41e3a) → 符合政务系统视觉习惯
- 浅灰背景(#f5f6f8) + 纯白卡片 → 长时间阅读不疲劳
- 违规表达式引擎用深色 → 专项分析工具可以不同，但主界面必须庄重

### 2. 为什么不做聊天式交互？

聊天式(如ChatGPT)适合探索性场景，但不适合审计工作流：
- 审计有固定程序，不是自由对话
- 审计结论需要溯源，聊天记录难以作为证据链
- 审计需要结构化输出(取证单/底稿/报告)，不是对话文本

法规问答模块保留对话式，因为它是探索性的。智能分析流程用步骤式向导。

### 3. 为什么每个确认点不能跳过？

审计责任在审计人员，不在AI。

如果AI推荐了错误法规、提取了错误数据、生成了错误结论，责任在谁？
→ 在审计人员。因为最终是**人**确认的。
→ 如果系统允许跳过确认，责任边界就模糊了。

### 4. 为什么案例库要三向关联？

传统案例库是"案例列表"。
AuditWorkbench的案例库是"知识枢纽"。

```
案例 → 违规模型 → 法规依据 → 定性结论
  ↑                           ↓
  └──── 同类案例 ← 同一定性 ←──┘
```

这个关联网络让审计人员可以：
- 从案例找到适用的违规模型
- 从违规模型找到法规依据链
- 从法规找到所有引用它的案例
- 从定性结论找到同类案例参考

## 六、信息架构

### 为什么不按功能类型分组，而按工坊分组？

传统分组(知识库/工具/设置)是**程序员视角**。
工坊分组(知识/数据/资料)是**审计工作视角**。

审计人员的思维是：
1. 我需要什么知识？→ 知识工坊
2. 我的数据能说明什么？→ 数据工坊
3. 我的材料怎么处理？→ 资料工坊

### 层级设计

```
首页 (一览全局)
 └─ 审计项目 (具体工作入口)
     └─ 智能分析 (核心流水线)
         ├─ 步骤间: 上一步输出 = 下一步输入
         └─ 步骤内: AI推荐 → 人工确认 → 自动执行
```

- 导航最多3层，常用功能2层可达
- 智能分析是深度工作的入口，不作为顶层导航(减少认知负担)
- 三大工坊平级，体现同等重要性

## 七、待解决的设计问题

1. **移动端适配深度**: 审计人员主要在PC工作，移动端做到"可查看"即可，不需要完整的移动操作流
2. **多用户协作**: 当前设计聚焦单人工作流，后续需考虑主审/审计员/复核人的协作模式
3. **离线能力**: 政府网络环境可能受限，需考虑内网部署方案
4. **数据安全**: 审计资料涉密，需考虑传输加密和本地存储方案
