## 一、方案定位与执行原则

领导愿景把审计工坊定位为「以审计项目为核心、以资料资产为基础、以数据工坊为支撑、以 AI 智能分析为能力、以全过程溯源为保障的智能审计操作系统」。当前代码库已经具备「项目、资料、OCR、结构化数据、违规模型、法规、分析、疑点、文书」的全部模块，但模块尚未按真实审计顺序形成**受控主链路**，AI 分析存在上下文污染，溯源停留在文档级，数据分析存在绕过项目结构化数据的入口。

本方案不做功能扩张，只做「真实业务链路补齐 + 智能分析引擎升级 + 底层能力建设」三件事，把领导愿景落到现有代码上。

### 1.1 与领导愿景的对应关系

| 领导愿景板块 | 本方案对应章节 |
|---|---|
| 二-一：审计项目生命周期管理 | 4.1 + Phase 1 |
| 二-二：资料工坊 | 4.2 + Phase 2 |
| 二-三：文档智能解析与溯源体系 | 4.3 + Phase 3/4 |
| 二-四：数据工坊 | 4.4 + Phase 5 |
| 二-五：智能分析七步流程 | 4.5 + Phase 8 |
| 二-六：AI 伴随机制 | 4.6 + Phase 8 |
| 二-七：底层能力（状态机/血缘/溯源/上下文/留痕/权限） | 4.7 + Phase 6/8 |
| 最终闭环（项目→资料→解析→数据→知识→分析→疑点→文书→归档） | Phase 9 端到端验收 |

### 1.2 三条核心建设原则的执行映射

| 领导原则 | 开发执行方式 |
|---|---|
| 原则一：AI 不能替代流程，系统状态驱动流程 | 后端项目状态机（`setup_stage`）控制阶段准入，前端 Tab/按钮只按后端返回的 `allowed_actions` 切换；AI 只做阶段内推荐，不做跨阶段生成 |
| 原则二：所有 AI 结果必须结构化（结论+来源+引用+置信度+关联对象） | 统一溯源对象 `audit_source_refs` + 步骤总结表 `audit_step_summaries`；无来源引用的结果标记「待人工核实」，不得自动确认 |
| 原则三：溯源能力必须提前建设 | Phase 3/4 优先完成 chunk 落库 + 字段级溯源；法规/疑点/文书全部复用同一证据链 |

### 1.3 七条执行原则（本方案开发纪律）

1. **智能分析后置**：智能分析安排在基础业务、OCR、溯源、数据工坊、安全和知识规则全部完成之后，最后开发七步 Agent 编排、AI 伴随和文书生成。
2. **契约先行**：现在只冻结智能分析数据契约（见附录A + `dev-specs/04-analysis-engine-contracts.md`），**不实现智能分析功能**。
3. **小功能拆分**：每个 Phase 拆成独立、可验证的小功能（0.5-2 个工作日/个，超过 3 天说明拆分不够细）。
4. **逐个通过**：每个小功能测试通过后才进入下一个功能。
5. **阶段验收门**：每个 Phase 设置阶段验收门，不允许带着失败项进入下一 Phase。
6. **兼容与回滚**：每个小功能都保持现有接口兼容，并提供回滚点。
7. **垂直切片**：每个小功能是一次端到端闭环（必要 DDL + Service + API + 前端行为 + 单元测试 + 集成测试 + 验收），不采用"先建全部表→再写全部后端→再统一前端→最后测试"的纯分层开发。

## 二、范围与约束

### 2.1 纳入范围

- 审计项目四阶段生命周期与阶段准入（立项 → 对象范围 → 事项 → 资料空间）。
- 资料工坊年度、项目、资料类型隔离（对象前缀 + workspace manifest，不建 MinIO 空目录）。
- 文件上传 → OCR → 切片 → 信息抽取 → 结构化落库 → 全链路溯源。
- 数据工坊结构化数据只经 `data_*` 表供给智能分析，原始文件仅用于查看复核。
- 安全与日志：用户—项目—角色权限、操作留痕、阶段变更日志、OCR 任务监控与告警。
- 知识库与分析规则：违规/法规/条款/案例查询、违规关联、字段映射、表达式规则（确定性知识）。
- 七步智能分析引擎：分析入口检查、数据准备检查、证据完整性检查、AI 上下文装配。
- 底层能力：项目状态机、数据血缘、操作留痕、权限控制（强制 project_id）。

### 2.2 明确不做

- 不新增与真实业务主链路无关的功能。
- 不改变 `projects.html` / `docworkshop.html` / `dataworkshop.html` / `analysis.html` 的现有视觉结构和主要交互方式。
- 不重写 `frontend/js/app.js` 导航框架。
- 不改动已有字段含义；同一业务含义优先映射到现有字段。
- 不让前端迁就后端；后端 DTO 继续兼容 `frontend/js/api.js` 现有格式。
- 不让 LLM 脱离当前项目、已确认数据和来源证据自由生成。
- 不新建音频算法能力；音频桶仅规划目录与接口，转写对接既有服务（待确认）。
- 本轮不实现智能分析功能（仅冻结契约，见执行原则 2）。

## 四、总体技术方案

### 4.1 项目生命周期与状态机

严格四阶段受控流程，**两个状态字段职责分离，"active" 只在 status 出现**：

| 字段 | 语义 | 取值 | 变化时机 |
|---|---|---|---|
| `setup_stage` | 立项流程进度 | `basic → target_scope → items → workspace` | 阶段推进时变，**不含 active** |
| `status` | 项目生命周期 | `draft / active / completed / archived` | workspace 完成 → draft 转 active |

```
阶段1 审计立项    → 只保存基础字段，status=draft，不建 bucket
   ↓ 字段白名单
阶段2 对象和范围   → 更新同一 project_id 的对象/范围字段
   ↓ 对象+范围必填
阶段3 审计事项     → AI 推荐 + 人工增删改；保存 audit_items
   ↓ 至少一项已确认
阶段4 创建资料空间 → 年度+project_id+项目名创建空间（幂等）；status=active
```

阶段准入矩阵（后端强制，前端只按返回的 `allowed_actions` 切换）：

| setup_stage | allowed_actions | 不可执行 |
|---|---|---|
| basic | save_basic | target_scope/items/finalize/upload/analysis |
| target_scope | save_basic, save_target_scope | items/finalize/upload/analysis |
| items | save_basic, save_target_scope, save_items, split_items | finalize/upload/analysis |
| workspace | save_basic, finalize, upload, analysis | — |

**字段—阶段矩阵（全部复用现有字段 + 已确认增量列）：**

| 业务信息 | 复用字段 | 阶段 |
|---|---|---|
| 项目名称/编号/描述 | `name` / `project_code` / `description` | 1 |
| 审计类型/方式/层级 | `audit_type` / `audit_method` / `target_level` | 1 |
| 被审计单位 | `audited_unit`（兼作主要审计对象） | 1 |
| 审计目标/期间/金额 | `objective` / `audit_period` / `amount` | 1 |
| 业务发生时间（起/止） | `business_start_date` / `business_end_date`（增量列，方案A） | 1 |
| 审计对象/延伸单位/范围/重点 | `scope` + 待补持久化字段 | 2 |
| 审计事项 | `audit_items` 表 | 3 |
| 审计年度 | 由 `audit_period` 起始日期派生（后端统一计算，决策 12） | 派生 |

### 4.2 资料工坊（对象前缀 + workspace manifest）

保留「每项目独立 bucket」的物理隔离，**不创建 MinIO 空目录**（空目录是零字节标记对象，是反模式），用对象前缀 + `workspace-manifest.json` 作为资料树单一事实源：

```
bucket: audit-project-{project_id}
└─ {audit_year}/{project_id}-{项目名安全短名}/
   ├─ project-materials/
   ├─ text/{word,pdf,excel,txt}/
   ├─ audio/{original,transcript}/
   ├─ image/  video/  other/
   └─ workspace-manifest.json     ← 年度/项目/类型/文件索引
```

要点：
- 年度是查询与对象前缀的一级逻辑维度；项目以 `project_id` 为唯一隔离键。
- 文件类型由后端 MIME/扩展名/解析结果判定，前端不承担目录规则。
- manifest 与实际对象可能漂移，需「列 MinIO 对象 vs manifest 对账」规则兜底（Phase 2 验收项）。
- 上传 API 保持现有路径兼容，由后端把文件落入正确前缀。

### 4.3 文档智能解析与溯源（分两阶段：解析 + 溯源）

**Phase 3（解析）**：保证「解析正确」——上传→trace→OCR→Markdown→分类→提取→写 data_* 表。

**Phase 4（溯源）**：保证「可追踪」——OntoSKU ID 落库、chunk 逐条落库、字段匹配 chunk、数据行关联 trace、统一证据引用、trace 查询、前端展示、重解析后旧证据失效。

```
文件上传(project_id)
  → 校验项目 active 且空间已创建
  → MD5 去重 → MinIO 分类路径 → audit_document_traces
  → 异步 OCR（OntoSKU，失败降级 LiteParse）
  → Markdown + chunks + 页图引用
  → chunk 逐条落库 audit_document_chunks
  → 文档分类 + 字段抽取（每字段绑定 chunk，写 audit_field_sources）
  → 写入对应 data_* 表（document_trace_id 关联）
  → 重解析：新 ocr_version，旧证据 superseded（见 Phase 4）
```

溯源层级（统一证据契约）：原始文件 → 文档切片 → 结构化字段 → 规则与知识 → Agent 执行 → 业务结论。

### 4.4 数据工坊

数据流向：**资料工坊 → OCR → 信息抽取 → 结构化表 → 智能分析调用**。

强制规则：
- 智能分析只读**当前 project_id** 下的 `data_*` 表，禁止直接读原始文件全文。
- 所有数据工坊查询在服务层自动附加 `project_id`，不信任 LLM 生成该条件。
- `data/<table>/rows` 分两种模式：**全局浏览**（明确无 project_id，只读列表）vs **项目分析**（强制 project_id）。
- 采购/访谈数据表映射按决策 8 确认。

### 4.5 智能分析引擎（Phase 8，先冻结契约）

七步流程：意图确认 → 方法推荐 → 法规确认 → 资料准备 → 数据比对 → 疑点核实 → 文书生成。三道控制层检查（入口/数据准备/证据完整性）。完整契约见附录A + `dev-specs/04-analysis-engine-contracts.md`，**本轮只冻结、不实现**。

**步骤驱动规则（4.5.5，Phase 8 落地）**：

```
用户点击「确认并进入下一步」→ POST 确认接口（携带已确认 ID）
  → 后端三道检查 → 推进步骤 → 计算本步结果 → 持久化 step_data
  → 返回权威状态 {step, status, 本步数据, 已确认ID, 来源引用}
  → 前端照返回的状态渲染
```

- 前端 = 渲染器 + 确认器（删除 `this.step` 自推进与关键词驱动，恢复从后端读）。
- 后端 = 状态源 + 计算器（`audit_analysis_tasks` 唯一权威）。
- LangGraph = 每步内部可选的 Agent 编排引擎，不要求前端跟随 interrupt 协议。
- 第 7 步文书走独立 `documents/batch`，后端逻辑记为 step 7。

### 4.6 AI 伴随收敛（Phase 8）

三类信息严格分离：页面状态 / Toast 反馈 / 审计日志 一律不进聊天、不进 LLM；`audit_step_summaries` 存每步一条固定 ID 正式总结（`step-1-summary` 至 `step-7-summary` 覆盖）；LLM 输入由 `AnalysisContextBuilder` 从 DB 装配。

### 4.7 底层能力（Phase 6 安全/日志 + Phase 8 智能分析侧）

| 能力 | 实现方式 | 落地 |
|---|---|---|
| 项目状态机 | `setup_stage` + `allowed_actions` | Phase 1 |
| 数据血缘 | `audit_source_refs` + `audit_field_sources` | Phase 4 |
| 文档溯源 | `audit_document_chunks` + trace 接口 | Phase 4 |
| 权限控制 | 用户—项目—角色矩阵 + 服务层强制 project_id | Phase 6 |
| 操作留痕 | `audit_logger` 扩事件类型 + 阶段变更日志 | Phase 6 |
| AI 上下文管理 | `AnalysisContextBuilder` | Phase 8 |
| Agent 溯源 | `BaseAgent._persist_trace()`（F3 需先补） | Phase 8 |

## 十三、待领导确认的决策（Phase 0 必答）

1. 「立项单位」是否等同当前创建人/所属组织；若不是，确认页面现有哪个字段承载。
2. 审计年度统一取审计期间起始年份，还是项目开始日期年份（建议取审计期间起始年份）。
3. `f-target-unit` 与 `f-unit` 是否同一业务含义；若不同，审计对象是否允许多个单位。
4. 延伸审计单位、报告文号、项目开始日期、进点日期、审计重点是否纳入本轮「现有字段补持久化」。（✅ 已确认：除报告文号外全部纳入；报告文号留到文书阶段）
5. 旧项目阶段迁移是否允许按现有数据自动推断后批量人工确认。（✅ 已确认：允许自动推断 + 人工批量确认）
6. 无精确条款或无文档页码的 AI 推荐，是否统一标记「待人工核实」并禁止进入最终文书（建议是）。
7. 音频转写是否本轮只规划目录和接口，后续再对接既有转写服务（建议是）。
8. 采购数据、访谈数据是新增 `data_*` 表，还是映射 `data_general`。（✅ 已确认：新增两张骨架表 `data_procurements` / `data_interviews`，采购表先充实字段、访谈表先占位）
9. **项目文档语义检索**：是否补项目 chunks 向量索引，还是本轮只走结构化 + 关键词（建议：只走结构化+关键词，向量检索入 backlog）。
10. **LLM 故障降级**：LLM 不可用时是否允许纯规则降级，结果强制标记「非 AI 推理」（建议是）。
11. **数值单位契约**：全库金额类字段统一按「元」存储（建议是，避免阈值比对差万倍）。
12. **审计年度派生口径**：统一取「第一个年份」，无法解析兜底创建年份并标记来源（建议是）。
13. **业务发生时间**：按方案A理解（被审计业务实际发生起止时间），新增两个 DATE 列（**已确认方案A，待定是否必填**）。

## 附录A：智能分析引擎接口契约要点（Phase 8 冻结，本轮不实现）

> 完整 JSON Schema 契约见 `docs/dev-specs/04-analysis-engine-contracts.md`（开发规格 v1）。本附录仅保留评审要点。

### A.1 通用约定

- 输入一律由服务端从 DB 装配（`AnalysisContextBuilder`），前端只传 `task_id + 已确认 ID + 页面操作`。
- 输出必须携带 `source_refs`；无来源条目标记 `confirm_status: "待人工核实"`，禁止进入最终文书。
- 步骤推进由「确认并进入下一步」驱动，禁止自然语言关键词驱动。

### A.2 七步契约要点

| 步骤 | 输入要点 | 输出要点 | 关键约束 |
|---|---|---|---|
| Step1 意图确认 | project_id + focus_item_id + intent | `analysis_task` | project_context 仅来自 DB，AI 不得重写 |
| Step2 方法推荐 | analysis_task | violation_candidates（+ engine_rule + audit_methods） | match_score 规则排序非 AI 打分 |
| Step3 法规确认 | analysis_task + confirmed_violations + 项目资料 | law_recommendations（law_id/clause_id/原文/位置） | 无条款或无原文 → 待人工核实 |
| Step4 资料准备 | analysis_task + data_requirements | readiness 报告 | 7 项检查全通过才可进 Step5 |
| Step5 数据比对 | confirmed_violations + engine_rules + data_* | exec_results（逐行证据 field_sources→chunk） | 只读 data_*，禁读原始文件 |
| Step6 疑点核实 | Step5 命中 + 已确认法规 | suspicion_candidates（五态） | 命中≠成立，须人工确认 |
| Step7 文书生成 | 已确认疑点 + 证据 + 法规 | documents 四件套（证据继承） | AI 只组织语言，不创造事实 |

### A.3 三道控制层检查（固定检查项）

| stage | 触发点 | name 枚举 | source |
|---|---|---|---|
| entry | Step1 前 | 项目完成 / 对象范围完成 / 事项完成 / 空间存在 / 权限正确 | `audit_projects.setup_stage`、`audit_items` |
| data_ready | Step5 前 | 文件存在 / OCR完成 / 分类完成 / 结构化完成 / 进入data_* / 字段完整 / trace存在 | `audit_document_traces`、`audit_document_chunks`、`data_*`、`audit_field_sources` |
| evidence_complete | Step7 前 | 疑点已确认 / 数据证据存在 / 文档引用存在 / 法规存在 | `project_suspicions`、`audit_source_refs` |

### A.4 疑点五态流转

| 当前状态 | 人工动作 | 下一状态 |
|---|---|---|
| MODEL_FOUND | 系统生成疑点候选 | WAIT_CONFIRM |
| WAIT_CONFIRM | 确认 / 判定不成立 / 证据不足 | CONFIRMED / REJECTED / NEED_MORE_EVIDENCE |
| NEED_MORE_EVIDENCE | 补充资料后重新确认 | WAIT_CONFIRM |
