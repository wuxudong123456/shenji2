## 一、方案定位

领导愿景把审计工坊定位为「以审计项目为核心、以资料资产为基础、以数据工坊为支撑、以 AI 智能分析为能力、以全过程溯源为保障的智能审计操作系统」。当前代码库已经具备「项目、资料、OCR、结构化数据、违规模型、法规、分析、疑点、文书」的全部模块，但模块尚未按真实审计顺序形成**受控主链路**，AI 分析存在上下文污染，溯源停留在文档级，数据分析存在绕过项目结构化数据的入口。

本开发方案不做功能扩张，只做「真实业务链路补齐 + 智能分析引擎升级 + 底层能力建设」三件事，把领导愿景落到现有代码上。

| 领导愿景板块 | 本文档对应章节 |
|---|---|
| 二-一：审计项目生命周期管理 | 第四章 4.1 + 第五章 Phase 1 |
| 二-二：资料工坊 | 第四章 4.2 + Phase 2 |
| 二-三：文档智能解析与溯源体系 | 第四章 4.3 + Phase 3 |

### 1.2 三条核心建设原则的执行映射

| 领导原则 | 开发执行方式 |
|---|---|
| 原则一：AI 不能替代流程，系统状态驱动流程 | 后端项目状态机（`setup_stage`）控制阶段准入，前端 Tab/按钮只按后端返回的 `allowed_actions` 切换；AI 只做阶段内推荐，不做跨阶段生成 |
| 原则二：所有 AI 结果必须结构化（结论+来源+引用+置信度+关联对象） | 统一溯源对象 `audit_source_refs` + 步骤总结表 `audit_step_summaries`；无来源引用的结果标记「待人工核实」，不得自动确认 |
| 原则三：溯源能力必须提前建设 | Phase 3 优先完成 chunk 落库 + 字段级溯源；法规/疑点/文书全部复用同一证据链 |

## 二、范围与约束

### 2.1 纳入范围

- 审计项目四阶段生命周期与阶段准入（立项 → 对象范围 → 事项 → 资料空间）。
- 资料工坊年度、项目、资料类型隔离。
- 文件上传 → OCR → 切片 → 信息抽取 → 结构化落库 → 全链路溯源。
- 数据工坊结构化数据只经 `data_*` 表供给智能分析，原始文件仅用于查看复核。
- 七步智能分析引擎：分析入口检查、数据准备检查、证据完整性检查。
- AI 伴随收敛：操作不产生聊天消息，每步一条固定 ID 正式总结，LLM 输入走结构化契约。
- 方法推荐、法规依据推荐、事项推荐的项目上下文约束与溯源绑定。
- 底层能力：项目状态机、数据血缘、操作留痕、权限控制（强制 project_id）。

### 2.2 明确不做

- 不新增与真实业务主链路无关的功能。
- 不改变 `projects.html` / `docworkshop.html` / `dataworkshop.html` / `analysis.html` 的现有视觉结构和主要交互方式。
- 不重写 `frontend/js/app.js` 导航框架。
- 不改动已有字段含义；同一业务含义优先映射到现有字段。
- 不让前端迁就后端；后端 DTO 继续兼容 `frontend/js/api.js` 现有格式。
- 不让 LLM 脱离当前项目、已确认数据和来源证据自由生成。
- 不新建音频算法能力；音频桶仅规划目录与接口，转写对接既有服务（待确认）。

## 四、总体技术方案

### 4.1 项目生命周期（对齐愿景「三」）

严格四阶段受控流程，后端状态机驱动：

```
阶段1 审计立项        → 只保存基础信息，status=draft
   ↓ 后端校验基础字段白名单
阶段2 审计对象和范围   → 更新同一 project_id 的对象/范围字段
   ↓ 后端校验对象+范围必填
阶段3 审计事项         → AI 基于 DB 项目上下文检索推荐；人工增删改；保存 audit_items
   ↓ 后端校验至少一项已确认事项
阶段4 创建资料空间     → 按年度+project_id+项目名创建空间；status=active（幂等）
```

**字段—阶段矩阵（全部复用现有字段）：**

| 业务信息 | 复用字段 | 阶段 |
|---|---|---|
| 项目名称/编号/描述 | `name` / `project_code` / `description` | 1 |
| 审计类型/方式/层级 | `audit_type` / `audit_method` / `target_level` | 1 |
| 被审计单位 | `audited_unit`（兼作主要审计对象） | 1 |
| 审计目标/期间/金额 | `objective` / `audit_period` / `amount` | 1 |
| 审计对象/延伸单位/范围/重点 | `scope` + 待补持久化字段 | 2 |
| 审计事项 | `audit_items` 表 | 3 |
| 审计年度 | 由 `audit_period` 起始日期派生（后端统一计算） | 派生，不入表单 |

### 4.2 资料工坊（对齐愿景「四」）

保留「每项目独立 bucket」的物理隔离，通过对象前缀实现年度与类型视图：

```
bucket: audit-project-{project_id}
└─ {audit_year}/{project_id}-{项目名安全短名}/
   ├─ project-materials/        项目资料桶
   ├─ text/{word,pdf,excel,txt}/  文本资料桶
   ├─ audio/{original,transcript}/ 音频资料桶（转写对接既有服务）
   ├─ image/                    图片资料桶（愿景新增）
   ├─ video/                    视频资料桶（愿景新增）
   └─ other/                    其他资料桶
```

要点：
- 年度是资料工坊查询与对象前缀的一级逻辑维度；项目仍以 `project_id` 为唯一隔离键，项目名只作展示与安全短名。
- `minio_bucket` 字段含义不变；文件类型由后端 MIME/扩展名/解析结果判定，前端不承担目录规则。
- 上传 API 保持现有路径兼容，由后端把文件落入正确前缀。

### 4.3 文档智能解析与溯源（对齐愿景「五、六、七」）

实现「AI 结论 → 证据 → 原文 → 文件位置」的完整证据链：

```
文件上传(project_id)
  → 校验项目 active 且空间已创建
  → 文件 MD5 去重（同项目内）
  → MinIO 分类路径
  → audit_document_traces 主记录（+ external_document_id / external_job_id / parse_engine / parse_status / parsed_at）
  → 异步 OCR/OntoSKU 任务
  → Markdown + chunks + 页图引用
  → chunk 逐条落库 audit_document_chunks（trace_id/project_id/chunk_id/type/page_nums/bbox/text/section）
  → 文档分类 + 模板匹配
  → 字段抽取（每字段绑定 chunk，写 audit_field_sources）
  → 写入对应 data_* 表（document_trace_id 关联）
  → 文件状态 = 可分析
```

溯源层级（统一证据契约，各业务模块复用）：

| 层级 | 必备标识 | 能回答的问题 |
|---|---|---|
| 原始文件 | project_id、trace_id、minio_path、MD5 | 来自哪个项目和文件 |
| 文档切片 | chunk_id、page_nums、bbox、原文 | 文件的哪一页哪一段 |
| 结构化字段 | table、row_id、field_name、chunk_id | 这个字段值如何提取 |
| 规则与知识 | violation_id、law_id、clause_id、case_id | 用了什么规则/法规/案例 |
| Agent 执行 | agent_trace_id、input refs、tool calls | AI 读取了哪些来源、做了什么调用 |
| 业务结论 | result_id、source refs | 事项/推荐/疑点/文书由哪些证据支撑 |

### 4.4 数据工坊（对齐愿景「八」）

数据流向：**资料工坊 → OCR → 信息抽取 → 结构化表 → 智能分析调用**。

现有六类结构化表与愿景数据类型的映射：

| 愿景数据类型 | 现有表 | 说明 |
|---|---|---|
| 合同数据 | `data_contracts` | ✅ 已具备 |
| 财务数据 | `data_finance` | ✅ 已具备 |
| 法律文书/登记/证照 | `data_legal_docs` / `data_registers` / `data_credentials` | ✅ 已具备 |
| OCR 结构化数据 | `data_general` | ✅ 已具备 |
| 采购数据 | 映射 `data_general` 或新增表 | ⚠️ 待领导确认 |
| 访谈数据（音频转写） | 映射 `data_general` 或新增表 | ⚠️ 待领导确认 |
| 审计分析数据 | `audit_analysis_tasks` + `project_suspicions` | ✅ 已具备 |

强制规则：
- 智能分析只读**当前 project_id** 下的 `data_*` 表，禁止直接读原始文件全文进行分析。
- 所有数据工坊查询在服务层自动附加 `project_id`，不信任 LLM 生成该条件。
- 空 project_id 的项目智能分析请求必须失败。

### 4.5 智能分析引擎（对齐思维导图文档「三、四、五、六」）

从「七步页面」升级为「引擎工作流」，增加三道后台控制层检查（不增加用户页面步骤）：

```
分析入口检查（Step1 前）：
  项目完成 && 对象范围完成 && 审计事项完成 && 资料空间存在 && 权限正确
   ↓
Step1 审计意图确认  → 读取项目上下文+audit_items，生成结构化分析任务
Step2 方法推荐      → 违规知识库→候选违规模型→人工确认→方法库映射→数据字段要求→分析规则
Step3 法规依据确认  → 项目资料+OCR内容+法规库，输出 法规名称/条款/引用来源
Step4 资料与数据准备→ 分析准备度检查（见下）
数据准备检查（Step5 前）：
  文件存在 && OCR完成 && 分类完成 && 结构化完成 && 进入data_* && 字段完整 && trace存在
   ↓
Step5 项目数据比对  → 结构化数据→规则计算→命中记录→证据引用
Step6 疑点人工核实  → MODEL_FOUND → WAIT_CONFIRM → CONFIRMED/REJECTED/NEED_MORE_EVIDENCE
证据完整性检查（Step7 前）：
  疑点已确认 && 数据证据存在 && 文档引用存在 && 法规存在
   ↓
Step7 审计文书生成  → AI 只负责语言组织，不负责事实创造
```

疑点状态机（思维导图文档定义）：`MODEL_FOUND → WAIT_CONFIRM → CONFIRMED / REJECTED / NEED_MORE_EVIDENCE`。

#### 4.5.1 核心产物：结构化分析任务 analysis_task（思维导图「四」落地）

思维导图要求 AI 上下文模型输出一个结构化 `analysis_task` 作为全链路唯一任务对象，而不是散落的聊天上下文：

```json
{
  "task_id": "analysis_task_id",
  "project_id": "A001",
  "project_context": { "name": "", "audit_type": "", "target_level": "" },
  "audit_items": ["已确认事项ID"],
  "audit_item": "采购付款异常分析",
  "target": "供应商付款合规性",
  "scope": "2025年度采购付款",
  "current_step": 2,
  "confirmed_results": {},
  "source_refs": []
}
```

落库方式：现有 `audit_analysis_tasks` 做增量列 `focus_item_id / analysis_target / analysis_scope`，`step_data / agent_results` 继续承载各步结果，不新建设计之外的表。完整输入/输出契约见附录A §A.2。

#### 4.5.2 核心模型链落库（思维导图「五-Step2」落地）

Step2 不能是「项目描述 → LLM → 方法」，必须是数据驱动映射链：**违规模型 → 审计方法 → 数据字段要求 → 分析规则**。当前仅 `audit_violations.expression_text` 承载分析规则，四者无关联结构。新增引擎映射表（见 6.2 ⑨）：

```text
audit_violations（违规模型）
   └─ audit_engine_rules（违规→目标表/表达式/字段映射/阈值）
   └─ audit_item_methods（违规→审计方法→数据字段要求）
```

二者均为知识库性质（不挂 project_id），Step2 按项目上下文检索，供 AI 排序解释，不由 LLM 凭空创造方法。Step2 输入/输出契约见附录A §A.3。

#### 4.5.3 三道控制层检查落地（思维导图「六」）

| 检查 | 触发点 | 检查项 | 数据源 |
|---|---|---|---|
| 分析入口检查 | Step1 前 | 项目完成 / 对象范围完成 / 事项完成 / 空间存在 / 权限正确 | `audit_projects.setup_stage` + `audit_items` |
| 数据准备检查 | Step5 前 | 文件存在 / OCR完成 / 分类完成 / 结构化完成 / 进入data_* / 字段完整 / trace存在 | `audit_document_traces` + `audit_document_chunks` + `data_*` + `audit_field_sources` |
| 证据完整性检查 | Step7 前 | 疑点已确认 / 数据证据存在 / 文档引用存在 / 法规存在 | `project_suspicions` + `audit_source_refs` |

落地为 `GET /api/audit/analysis/{id}/readiness`（见第七章 API），返回逐项结果与缺失清单。统一检查契约见附录A §A.9，Step4 准备度契约见 §A.5。

#### 4.5.4 疑点五态状态机落库（思维导图「五-Step6」落地）

`project_suspicions.status` 现状为 draft/confirmed/rejected 三态。对齐引擎五态：`MODEL_FOUND → WAIT_CONFIRM → CONFIRMED / REJECTED / NEED_MORE_EVIDENCE`。为避免破坏现有字段语义，采用**增量列** `verify_status`（见 6.2 ⑩），`status` 保持兼容；前端疑点列表按 `verify_status` 渲染「待核实/已确认/不成立/需补证」徽标。Step6 契约与状态流转见附录A §A.7。

### 4.6 AI 伴随收敛（对齐愿景「十」与思维导图「四」）

三类信息严格分离：

| 信息类型 | 存放位置 | 是否进入聊天 | 是否进入 LLM |
|---|---|---|---:|
| 勾选/取消/拖拽/加载/按钮状态 | 页面状态 | 否 | 否 |
| 成功/失败/已选择等临时反馈 | Toast/状态文字 | 否 | 否 |
| 详细操作记录 | 审计日志 | 否 | 默认否 |
| 当前步骤业务状态 | 分析任务 `step_data` | 否 | 是（结构化输入） |
| 每步正式结论 | `audit_step_summaries` | 是，每步一条 | 是（必要时作上游结论） |
| 来源证据 | `audit_source_refs` | 通过溯源面板展示 | 只传引用和必要摘录 |

七条固定消息 ID 覆盖：`step-1-summary` 至 `step-7-summary`。返回修改只更新同一条 DOM 消息与同一条数据库记录，不追加。只有点击「确认并进入下一步」才生成/覆盖总结。

LLM 输入契约（服务端自行装配，不接受前端传 HTML）：

```json
{
  "project_id": "...",
  "task_id": "...",
  "step": 3,
  "project_context": { "basic": {}, "target_scope": {}, "audit_item_ids": [] },
  "confirmed_ids": { "violation_ids": [], "law_ids": [], "document_ids": [] },
  "step_result": {},
  "source_refs": ["ref-..."]
}
```

### 4.7 底层能力（对齐愿景「七」六项）

| 能力 | 实现方式 |
|---|---|
| 项目状态机 | `audit_projects.setup_stage` + `allowed_actions` 计算（后端返回，前端只切换状态） |
| 数据血缘 | `audit_source_refs`（结果→chunk/数据行/法规/违规/案例）+ 字段级 `audit_field_sources` |
| 文档溯源 | `audit_document_chunks` + 统一 `GET /traces/{type}/{id}` 查询接口 |
| AI 上下文管理 | `AnalysisContextBuilder` 服务，按 project/task/step 装配结构化上下文 |
| 操作留痕 | `audit_logger` 扩事件类型 + `audit_agent_traces` + `audit_step_summaries`（操作日志与对话分离） |
| 权限控制 | 服务层强制 project_id 隔离 + trace/数据访问项目归属校验 |

### 6.3 数据约束

- 所有新增证据表必须有 `project_id` 联合索引。
- `document_trace_id`、`chunk_id`、法规条款 ID、业务结果 ID 使用真实引用，不以标题文本替代。

- 旧项目按字段+事项做一次性阶段推断，人工确认后标记 active。

## 七、API 开发明细

保留现有 CRUD 全部兼容，新增语义接口；旧接口内部转调同一 service，避免双套逻辑。

| 建议接口 | 作用 | 关键校验 |
|---|---|---|
| `PUT /api/audit/projects/{id}/basic` | 保存立项基础信息 | 仅基础字段白名单 |
| `PUT /api/audit/projects/{id}/target-scope` | 保存对象和范围 | 项目存在、阶段1完成 |
| `POST /api/audit/projects/{id}/items/recommend` | 推荐事项 | 前两阶段完成；从 DB 读上下文和知识来源 |
| `PUT /api/audit/projects/{id}/items` | 保存人工确认事项（已存在） | 至少一项；记录差异日志 |
| `POST /api/audit/projects/{id}/workspace/finalize` | 创建资料空间并激活 | 四阶段完整；幂等 |
| `GET /api/audit/workspace/tree?year=` | 年度—项目—类型—文件树 | 服务端项目权限和年度过滤 |
| `GET /api/audit/traces/{result_type}/{result_id}` | 统一查询结论证据链 | project_id 权限、引用完整性 |
| `PUT /api/audit/analysis/{id}/summaries/{step}` | 覆盖步骤总结 | 固定 message_id、版本、来源 |
| `GET /api/audit/analysis/{id}/readiness` | 数据准备度检查（Step4/5 入口） | 文件/OCR/结构化/字段/trace 全检查 |

兼容要求：
- `POST /api/audit/projects` 响应字段不变，但不再第一阶段建 bucket。
- `GET /api/audit/projects/{id}` 继续返回原字段和 audit_items，只追加阶段信息。
- 文件、数据、知识、分析现有端点路径保持可用。

```
Phase 0(1周) → Phase 1(1-2周) → Phase 2(1周) → Phase 3(2周)
   → Phase 4(1周) → Phase 5(2周) → Phase 6(1-2周) → Phase 7(1周) → Phase 8(1周)
```

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M0 | 字段/口径确认 | 字段—阶段—表映射表签核 |

| M5 | AI 上下文收敛 | LLM 请求无 HTML；每步一条固定消息；返回修改只覆盖原消息 |
| M6 | 推荐可溯源 | 事项/法规/疑点/文书均能展开到规则/法规/案例/数据行/原文 |
| M7 | 端到端上线 | 全链路测试通过；旧接口灰度完成 |

## 十二、风险与应对

| 风险 | 控制措施 |
|---|---|
| 部分现有前端字段无 DB 映射 | Phase 0 字段盘点后由领导确认含义；只加同名映射，不改字段定义 |
| 旧项目没有阶段状态 | 一次性字段+事项推断，人工批量确认后再标记 active |

| OntoSKU 不可用触发降级 | 降级结果标明引擎和溯源等级；无页码不伪造坐标 |
| 旧前端仍调原接口 | 保留原路由并内部适配新 service，分阶段灰度 |
| LLM 推荐缺少证据 | 后端结果校验器：无来源条目进入「待人工补证」，不自动确认 |
| 项目名变更影响目录 | 关联始终用 project_id；显示名变化不迁移物理主键路径 |
| 采购/访谈数据无现成表 | Phase 0 确认映射或新增；不临时改现有表语义 |

## 十三、待领导确认的决策（Phase 0 必答）

1. 「立项单位」是否等同当前创建人/所属组织；若不是，确认页面现有哪个字段承载。
2. 审计年度统一取审计期间起始年份，还是项目开始日期年份（建议取审计期间起始年份）。
3. `f-target-unit` 与 `f-unit` 是否同一业务含义；若不同，审计对象是否允许多个单位。
4. 延伸审计单位、报告文号、项目开始日期、进点日期、审计重点是否纳入本轮「现有字段补持久化」。
5. 旧项目阶段迁移是否允许按现有数据自动推断后批量人工确认。
6. 无精确条款或无文档页码的 AI 推荐，是否统一标记「待人工核实」并禁止进入最终文书（建议是）。
7. 音频转写是否本轮只规划目录和接口，后续再对接既有转写服务（建议是）。
8. 采购数据、访谈数据（音频转写结果）是新增 `data_*` 表，还是映射 `data_general`（建议：采购→新增 `data_procurements`，访谈→新增 `data_interviews`，两个都仅含 `project_id/document_trace_id/raw_text/extra_fields` 基础骨架）。

## 十四、最终定位

本方案把领导愿景从「架构方向」落到「可执行的开发任务」：先让项目生命周期与数据隔离受控（P0），再建全链路证据链（P0），最后收敛 AI 上下文与推荐溯源（P1）。全程复用现有 Flask 路由、MySQL 六类表、OntoSKU 客户端、Agent、LangGraph、MinIO，避免在链路未受控时继续叠加智能功能。

## 附录A：智能分析引擎接口契约要点

> 完整 JSON Schema 契约见 `docs/dev-specs/04-analysis-engine-contracts.md`（开发规格 v1，随开发迭代升版）。本附录仅保留领导评审与排期所需的契约要点。

### A.1 通用约定

- 输入一律由服务端从 DB 装配（`AnalysisContextBuilder`），前端只传 `task_id + 已确认 ID + 页面操作`。
- 输出必须携带 `source_refs`（对应 `audit_source_refs`）；无来源条目标记 `confirm_status: "待人工核实"`，禁止进入最终文书。
- 步骤推进由「确认并进入下一步」驱动，禁止自然语言关键词驱动。

### A.2 七步契约要点

| 步骤 | 输入要点 | 输出要点 | 关键约束 |
|---|---|---|---|
| Step1 意图确认 | project_id + focus_item_id + intent | `analysis_task`（project_context / focus_item / target / scope） | project_context 仅来自 DB，AI 不得重写 |
| Step2 方法推荐 | analysis_task | violation_candidates（违规模型 + engine_rule + audit_methods + match_score） | match_score 为规则排序非 AI 打分；映射链来自 audit_engine_rules / audit_item_methods |
| Step3 法规确认 | analysis_task + confirmed_violations + 项目资料 | law_recommendations（law_id / clause_id / 条款原文 / 引用位置） | 无条款或无原文 → 待人工核实 |
| Step4 资料准备 | analysis_task + data_requirements 汇总 | readiness 报告（ready / checks / missing_items） | 7 项检查全通过才可进入 Step5 |
| Step5 数据比对 | confirmed_violations + engine_rules + 当前项目 data_* | exec_results（hit_rows 逐行证据 field_sources→chunk） | 只读 data_* 表，禁止直接读原始文件 |
| Step6 疑点核实 | Step5 命中 + 已确认法规 + 人工意见 | suspicion_candidates（verify_status 五态 + evidence_chain） | 命中≠成立，须人工确认 |
| Step7 文书生成 | 已确认疑点 + 证据 + 法规 + 人工意见 | documents 四件套（证据继承） | AI 只组织语言，不创造事实 |

### A.3 三道控制层检查（固定检查项）

| stage | 触发点 | name 枚举 | source |
|---|---|---|---|
| entry | Step1 前 | 项目完成 / 对象范围完成 / 事项完成 / 空间存在 / 权限正确 | `audit_projects.setup_stage`、`audit_items` |
| data_ready | Step5 前 | 文件存在 / OCR完成 / 分类完成 / 结构化完成 / 进入data_* / 字段完整 / trace存在 | `audit_document_traces`、`audit_document_chunks`、`data_*`、`audit_field_sources` |
| evidence_complete | Step7 前 | 疑点已确认 / 数据证据存在 / 文档引用存在 / 法规存在 | `project_suspicions`、`audit_source_refs` |

### A.4 疑点五态流转

| 当前状态 | 人工动作 | 下一状态 |
|---|---|---|
| MODEL_FOUND | 系统生成疑点候选 | WAIT_CONFIRM |
| WAIT_CONFIRM | 确认 / 判定不成立 / 证据不足 | CONFIRMED / REJECTED / NEED_MORE_EVIDENCE |
| NEED_MORE_EVIDENCE | 补充资料后重新确认 | WAIT_CONFIRM |
